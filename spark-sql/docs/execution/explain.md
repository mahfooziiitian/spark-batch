# :material-magnify-expand: EXPLAIN Plans

`EXPLAIN` shows how Spark will execute a query without running it. It is the primary tool
for diagnosing slow queries, verifying join strategies, and confirming predicate pushdown.

---

## :material-code-tags: Syntax

```sql
EXPLAIN [mode] statement;
```

| Mode | Alias | Output |
|------|-------|--------|
| *(none)* | `SIMPLE` | Physical plan only |
| `EXTENDED` | | Parsed → Analyzed → Optimized → Physical plans |
| `CODEGEN` | | Java source generated by whole-stage code gen |
| `COST` | | Optimized logical plan with row/size estimates (requires statistics) |
| `FORMATTED` | | Physical plan split into node tree + per-node detail table |

---

## :material-information-outline: Behavior

1. `EXPLAIN` **does not execute** the query — no data is read or written.
2. `EXPLAIN` without a mode is equivalent to `EXPLAIN SIMPLE` — physical plan only.
3. `EXPLAIN FORMATTED` is the most readable format for large plans; each operator appears once and its details are listed in a separate table below.
4. Operators prefixed with `*` in the physical plan participate in **Whole-Stage Code Generation** (fusion).
5. `EXPLAIN COST` returns `?` for estimates when column statistics have not been collected — run `ANALYZE TABLE ... COMPUTE STATISTICS FOR COLUMNS` first.
6. `EXPLAIN CODEGEN` is useful for diagnosing performance regressions caused by UDFs or non-fuseable operators breaking the code-gen chain.

## :material-flask-outline: Practical Examples

### Simple physical plan

```sql
EXPLAIN
SELECT department, COUNT(*) AS headcount
FROM employees
WHERE age > 30
GROUP BY department;
```

```
== Physical Plan ==
*(2) HashAggregate(keys=[department#10], functions=[count(1)])
+- Exchange hashpartitioning(department#10, 200), ENSURE_REQUIREMENTS
   +- *(1) HashAggregate(keys=[department#10], functions=[partial_count(1)])
      +- *(1) Filter (age#12 > 30)
         +- *(1) ColumnarToRow
            +- FileScan parquet [department#10, age#12]
               PushedFilters: [IsNotNull(age), GreaterThan(age, 30)]
               ReadSchema: struct<department:string,age:int>
```

Key observations:
- `PushedFilters` — the `age > 30` predicate was pushed to the Parquet reader.
- `*(1)` prefix — operators in stage 1 are fused into one code-gen method.
- `Exchange hashpartitioning` — a shuffle on `department` separates stage 1 from stage 2.
- Two-phase `HashAggregate` — partial aggregation on each executor, then final merge.

### Full plan at every stage

```sql
EXPLAIN EXTENDED
SELECT region, SUM(amount) AS total
FROM sales
WHERE order_date >= '2024-01-01'
GROUP BY region;
```

Read the four sections in order: Parsed → Analyzed → Optimized → Physical.
The Optimized plan shows predicate pushdown and column pruning applied.

### Formatted plan (recommended for complex queries)

```sql
EXPLAIN FORMATTED
SELECT
    c.name,
    SUM(o.amount) AS lifetime_value
FROM orders AS o
JOIN customers AS c
    ON o.customer_id = c.customer_id
WHERE o.order_date >= '2024-01-01'
GROUP BY c.name
ORDER BY lifetime_value DESC
LIMIT 20;
```

The formatted output separates the operator tree from per-operator statistics,
making it easier to spot the expensive node.

### Cost-based plan with statistics

```sql
-- Collect statistics first
ANALYZE TABLE orders COMPUTE STATISTICS FOR COLUMNS customer_id, order_date, amount;
ANALYZE TABLE customers COMPUTE STATISTICS FOR COLUMNS customer_id, name;

-- Now EXPLAIN COST shows real row/size estimates
EXPLAIN COST
SELECT c.name, SUM(o.amount)
FROM orders AS o
JOIN customers AS c ON o.customer_id = c.customer_id
GROUP BY c.name;
```

### Inspect code generation

```sql
EXPLAIN CODEGEN
SELECT customer_id, SUM(amount)
FROM orders
GROUP BY customer_id;
```

Look for `/* 001 */` through `/* 00N */` generated method blocks. A break in the
numbering (a new method starting at `/* 001 */`) indicates a fusion boundary caused
by a non-fuseable operator.

## :material-swap-horizontal: Reading a Physical Plan

```
*(2) HashAggregate(...)               ← stage 2, fused
+- Exchange hashpartitioning(...)     ← shuffle boundary (stage split)
   +- *(1) HashAggregate(...)         ← stage 1 partial agg, fused
      +- *(1) Filter (age > 30)       ← fused with scan
         +- FileScan parquet [...]    ← storage scan
              PushedFilters: [...]    ← filters pushed to reader
              ReadSchema: struct<...> ← column pruning applied
```

| Indicator | Meaning |
|-----------|---------|
| `*(N)` prefix | Whole-Stage Code Gen, stage N |
| `Exchange` | Shuffle — expensive; minimize these |
| `PushedFilters` | Filters executed by the storage reader |
| `ReadSchema` | Only these columns were read from disk |
| `BroadcastHashJoin` | Small table was broadcast — no shuffle for that side |
| `SortMergeJoin` | Both sides were shuffled and sorted |

## :material-lightbulb-outline: When to Use Each Mode

| Goal | Mode |
|------|------|
| Quick check of join strategy or filter pushdown | `EXPLAIN` (simple) |
| Trace a query rewrite or understand optimizer decisions | `EXPLAIN EXTENDED` |
| Debug a slow plan on a complex multi-join query | `EXPLAIN FORMATTED` |
| Verify statistics are being used in join ordering | `EXPLAIN COST` |
| Diagnose a UDF breaking whole-stage code gen | `EXPLAIN CODEGEN` |

!!! tip "Use EXPLAIN FORMATTED in notebooks"
    In Databricks / Jupyter notebooks, `EXPLAIN FORMATTED` renders the most human-friendly
    output. Pipe it through `spark.sql("EXPLAIN FORMATTED ...").show(truncate=False)` in
    PySpark to see the full untruncated plan.
